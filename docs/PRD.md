## 1. 배경 및 목적

국내 증권사(키움증권) API를 통해 개인 투자자가 자신의 거래 내역과 종목 정보를 통합적으로 조회·분석할 수 있는 개인용 웹 도구를 제공한다.

기존 증권사 HTS/MTS 및 네이버 증권 등에서는 다음과 같은 한계가 있다.

- **실현손익 조회 기간 제한**: 증권사 앱에서 실현손익을 조회할 수 있는 기간이 제한적이어서, 장기간에 걸친 손익을 한 번에 확인하기 어렵다.
- **기업 순위 정렬 기준의 한계**: 네이버 증권 등은 시가총액 기준 순위만 제공하며, ROE·PER 등 투자 지표 기준의 정렬/필터링을 지원하지 않는다. 키움 API에도 이를 직접 지원하는 단일 API가 없다.

Stock Manager는 키움증권 OpenAPI(REST)를 백엔드에서 수집·가공하여 DB에 적재하고, 사용자가 원하는 기간·조건으로 자유롭게 조회할 수 있는 화면을 제공하는 것을 목표로 한다.

### 대상 사용자

- 키움증권 계좌를 보유한 개인 투자자 (현재는 프로젝트 소유자 개인 사용을 전제로 한 단일 사용자 도구)
- 다중 계좌(복수 키움 계좌)를 보유한 사용자도 지원 대상에 포함

## 2. 제품 범위

### 2.1 In Scope

1. 계좌별 실현손익 조회 (기간 제한 없이 임의 구간 조회)
2. 계좌별 입출금/거래내역(현금흐름) 조회
3. 상장 종목 정보 수집 및 ROE/PER 등 투자 지표 기반 스크리닝(기업 순위 조회)
4. 키움 조건검색식 기반 종목 조회 (조건조회)
5. 다중 계좌 관리 (계좌 등록/조회, 계좌별 API 키 관리)

### 2.2 Out of Scope (현재 미지원, 명시적 확인 필요)

- 로그인/인증/권한 관리 (다중 사용자 지원) — 단일 사용자 개인 도구로 가정
- 키움 외 타 증권사 연동
- 매매 주문/체결 등 실거래 기능 (조회 전용 도구)
- 모바일 앱 (웹 전용, 반응형 지원 여부는 확인 필요)

## 3. 시스템 개요

Stock Manager는 React 기반 웹 프론트엔드와 Spring Boot 기반 백엔드 API, MariaDB로 구성된 웹 애플리케이션이며, 키움증권 OpenAPI를 유일한 외부 데이터 소스로 사용한다. 백엔드는 키움 API 응답을 단순 프록시하지 않고 DB에 적재·재사용함으로써, 외부 API의 레이트 리밋과 조회 기간 제약을 사용자가 인지하지 않도록 흡수하는 것을 핵심 설계 원칙으로 한다.

기술 스택, 아키텍처 다이어그램, 레이어 구조 등 기술적 상세는 [`TRD.md`](./TRD.md) 1~3장 참고.

## 4. 기능 요구사항

시스템이 제공해야 하는 기능 요구사항이다. 동작 방식·처리 로직·화면 상세는 [`FEATURES.md`](./FEATURES.md), 현재 구현 여부와 남은 작업은 [`TASK.md`](./TASK.md) 참고.

### 4.1 계좌 관리

사용자는 여러 개의 키움 계좌를 등록하여 관리할 수 있어야 하며, 각 계좌는 별칭·계좌번호·계좌 유형·키움 인증정보(앱키/시크릿키)를 가진다.

### 4.2 실현손익 조회 (자산관리)

증권사 앱은 실현손익 조회 가능 기간이 제한적이다. 사용자는 계좌와 임의의 조회 기간(기간 제약 없이), 선택적으로 특정 종목을 지정해 실현손익 내역을 확인할 수 있어야 한다.

### 4.3 입출금/거래내역(현금흐름) 조회

사용자는 계좌·기간·거래 구분(입출금/매매/대출/환전 등)으로 필터링하여 전체 거래 원장을 조회할 수 있어야 한다.

### 4.4 기업 조회 / 종목 스크리닝

사용자는 거래소 구분, ROE 범위, PER 범위를 조건으로 종목을 검색하고, 시가총액순으로 결과를 확인할 수 있어야 한다.

### 4.5 조건검색 (조건조회)

사용자가 키움 HTS에서 등록한 조건검색식 목록을 조회하고, 이를 활용해 종목을 검색할 수 있어야 한다.

### 4.6 종목 마스터/재무정보 자동 갱신

시스템은 최신 상장 종목 목록과 재무지표(ROE/PER 등)를 주기적으로 자동 수집하여, 4.4 종목 스크리닝 기능의 데이터 원천으로 제공해야 한다.

각 기능의 상세 사양은 [`FEATURES.md`](./FEATURES.md) 4.1~4.6, 현재 구현 상태와 남은 작업은 [`TASK.md`](./TASK.md) 참고.

## 5. 비기능 요구사항

제품 관점의 요구사항(원칙)만 기술한다. 현재 구현 상태, 기술 부채, 개선 과제 목록은 [`TRD.md`](./TRD.md) 8~12장 참고.

### 5.1 외부 API 제약의 투명한 처리
키움 API의 레이트 리밋 및 조회 기간 제약으로 인해 사용자의 조회 경험이 제한되어서는 안 된다. 시스템이 이러한 제약을 내부적으로 흡수하여, 사용자는 원하는 임의의 기간을 한 번의 조회로 요청할 수 있어야 한다.

### 5.2 데이터 재사용
동일한 데이터에 대한 반복 조회는 외부 API를 다시 호출하지 않고 저장된 데이터를 재사용하여, 응답 속도를 높이고 외부 API 호출량을 최소화해야 한다.

### 5.3 보안 (제품 정책)
현재는 2.2절(Out of Scope)에 따라 단일 사용자 개인 도구로 운영됨을 전제로 한다. 다중 사용자 지원 또는 외부 배포로 범위가 확장될 경우, 인증 체계 도입과 자격증명 보호 방식에 대한 재검토가 선행되어야 한다.

### 5.4 신뢰성 있는 오류 응답
API 오류 상황에서도 사용자(및 이를 소비하는 프론트엔드)가 원인을 파악할 수 있는 일관된 응답 형식을 제공해야 한다.

## 6. 향후 로드맵 제안 (우선순위 초안)

1. **입출금/거래내역 조회 화면 제공** — 4.3 요구사항 충족.
2. **기업(종목) 스크리닝 화면 제공** — 4.4 요구사항 충족.
3. **계좌 등록/관리 기능 제공** — 4.1 요구사항 충족, 실사용성 확보의 전제조건.
4. **조건검색(조건조회) 기능 제공** — 4.5 요구사항 충족.
5. **오류 응답 일관성 확보** — 5.4 요구사항 충족.
6. **Home 대시보드 제공** — 주요 지표(총 실현손익 요약 등) 노출.
7. **인증/보안 체계 검토** — 배포 범위 확대 시 5.3 요구사항 재검토.

우선순위 판단 근거(현재 구현 상태, 비용/효과 분석)와 실행 단위로 세분화된 작업 목록은 [`TASK.md`](./TASK.md) 참고.
